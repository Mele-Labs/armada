Where the tokens go

Reads cost about a fifth of the spend, so you are right that they matter, but what we're missing is the multiplier behind them. Spend is requests times context: 137,766 requests in 14 days, each re-sending 181k tokens on average, and 65% of all spend is re-reading what is already in context. Nothing leaves a context before 400k, every thread starts at 45k to 56k before it does any work, and agents take reading one step at a time. Four changes should save about 30%. Sharing knowledge between agents is the smallest of them, at 2% to 5%. I'm confident in the shares and less so in the savings, which come from a simulation.

What was decided

You chose a 250k compaction window for a week, replacing the 400k you set on 13 Oct. It is not switched on yet. You also chose a small trial of Fleet compacting a Job that is waiting on you, with the decision to build it coming after the trial. And you chose to make connectors a setting per repository, off for this one. Fleet would set ENABLE_CLAUDEAI_MCP_SERVERS=false when it starts a Job in a repository set that way, which Claude Code reads as not fetching your claude.ai connectors at all. Your account and connector settings stay as they are, and so do Claude Code sessions you start outside Armada. Servers a repository names itself, such as the browser and the code graph, are not affected. A repository you have not set keeps its connectors. You chose to leave the memory index alone. This page is otherwise the proposal. Two of your earlier decisions still stand: the 55-minute idle stop, and that Fleet never starts a fresh Job by itself.

Your earlier fixes held. Nothing runs above 400k any more. Fleet act replies are down to about 1% of spend. The whole-file guard keeps single reads small, and the largest in 14 days was about 27k tokens. About 75% of subagent spend is on Sonnet.

Your two questions about reading

Would sharing knowledge between agents help?

A little. It repays less than it looks, because a repeated read is cheap next to everything carried with it.

A shared store of files would not catch much. Agents read 10,643 distinct files, and the ten most read make up 6% of reading. The cheap form of sharing is a brief that names file:line, since the parent has usually found the place already.

Could agents know which files to look at from context clues?

We already have the tool for this and nobody uses it. In 14 days agents ran about 52,000 reading commands and asked the code graph 224 times. Only 4 of those asked where something is (query 3, context 1). Most were impact checks. Two things stand in the way:

  • The Logbook records that only the main checkout and slot-3 are registered, so a call from another slot's path comes back "not found".
  • The graph hook fired 12,696 times and added about 1M tokens, and it matches loosely. In this Job, a grep for "short account" got back short_of in headroom.rs, which has nothing to do with it. That teaches agents to ignore it.

The size of the prize is the part before work starts. The first edit comes at request 33 on main threads and request 30 on subagents. Threads that edit spend 21% of all spend before that first edit, and 8% of reading tokens are on files the thread also changes. I can't say how much of that a working graph would remove until we try it.

How agents read

70% of reading goes through Bash (41M tokens against 17M through Read, by the character estimate), so the whole-file guard never sees it. A guard would not help much there, because those reads are small, about 1k tokens each by the same estimate. The trouble is how many there are, one per round trip.

What we're missing

1. Nothing leaves a context

A grep result from step 20 is sent again on every later step. 64% of what tool results cost to carry comes from results at least 30 steps old. Claude Code does contain a way to clear old results, but it sits behind a remote switch that is off for us: 0 requests across 582 main threads used it. That leaves compaction as the only thing we control, and it happens late, at a median of 366k, falling to 74k.

The re-read column is reasonable: over the 20 steps after a compaction a thread grows 32k at the median, against 27k ordinarily, so real re-reading looks like 5k to 10k. What the table can't show is whether work gets worse after a compaction.

Going cold matters on its own. 656 times a main thread sat for over an hour and then rewrote 192k tokens on average, at the highest rate. That moment is the cheapest time to compact, since the whole context is being paid for anyway. Better still, Fleet could compact a Job waiting on you just before its cache expires, while reading it is still cheap.

Changing the cache lifetime doesn't help, and I tested it. Five minutes on main threads would cost 38% more on those threads. An hour on subagents would add about 3% to save at most 1.6%.

2. The start-up text costs more than all the reads

Each 10k tokens cut from start-up saves about 4.6% of spend, because it is carried on every request of every thread. A main thread starts at 56k and a subagent at 45k. The token figures below scale characters to that 56k.

3. Every step re-sends everything, and agents can't see that

At 181k of context, one small grep costs the same as about 18k tokens of fresh input, on top of its own output. 65% of main-thread requests and 89% of subagent requests carry a single tool call.

Main threads also do their own reading on Opus. armada:explorer took 246 of about 1,700 dispatches and cost 0.3% of spend, so reading is very cheap there, and only its report joins the main thread's context.

4. Nothing shows any of this

The Usage page weighs turns by token type only: Haiku counts the same as Opus, and an hour-long cache write counts as 1.25 when it costs 2. It also can't say what the tokens were, so none of the above would show up there, and a change that made things worse would go unnoticed.

The memory index split

You chose to leave the memory index alone, so it stays whole and on every request. I proposed moving your Bridge rules behind a list agents had to choose to read, and then moving 45 lines about finished work, and both are withdrawn. A rule that an agent can skip without anyone noticing isn't worth the 0.8% to 2% of spend they would have saved.

What was not measured

  • Dollars or your plan's real weighting. Shares use weights I assumed: Opus and Fable 5, Sonnet 3, Haiku 1, with cache read 0.1, write 1.25 or 2, and output 5. They are not read from a price list or from the plan meter.
  • Tokens per tool result. Transcripts hold characters. I calibrated on 296 Bash and 19 Read results, about 2.4 characters per token, and scaled tool results to match. Without that scaling, reading is 14% of spend, not 21%. The 19% row is what remains, so it absorbs any error.
  • Whether thinking stays in context. It looks like it does, but that rests on 14 samples.
  • Quality after compaction. Nothing here says whether a compacted Job does worse work or needs more of your time. That is the real risk in the first row.
  • Agents changing how they work. The simulation replays the same steps, and the round-trip and graph savings are estimates.
  • Whether reads were useful. Low reuse doesn't mean waste. Reading a file you don't change can be how you learn what to change.
  • Which file a Bash read touched is the first path in its command, so overlap figures are approximate.
  • Other Macs and anything before 21 Oct. This Mac's transcripts only. The scripts are in .armada/usage/ in this Job's slot.
