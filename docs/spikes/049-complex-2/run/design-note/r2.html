Dropping the state of gone Jobs

A Job counts as gone when Fleet's list no longer has it, or when it ended more than 7 days ago. Bridge drops a gone Job's arrangement and its Custom tab state on the first fresh read of the Job list after it starts, and again at most every 10 minutes while it runs, never for a live Job and never for a Job drawn in the window. Custom tab state gets keyed by Job and tab, so two Jobs that mint the same tab id each keep their own. Approve this and the two build groups start side by side.

When a Job counts as gone

Fleet's GET /sessions lists every Job it has ever held, across every repository, with no cutoff (crates/api/src/sessions.rs:721). An ended Job stays openable in Bridge: its thread, its panes and Fork.

OptionWhat it costs
A. Gone once it has endedReopening a Job that ended an hour ago shows the default layout and resets its Custom tabs. That changes how a layout looks while the Job still exists.
B. Gone once Fleet's list no longer has itFleet never forgets a Job, so this drops only keys of Jobs from another Fleet or a replaced store. The keys still grow without bound.
C. Gone once Fleet's list no longer has it, or it ended more than 7 days ago (by ended_at)Keys stay for a week after a Job ends. A Job reopened after that opens on the default layout, which is the layout for all. One constant to tune.

A live Job is never gone, and neither is a terminal Job Bridge shows as quiet: it is still live on the ledger and can come back. A Job with state: ended and no ended_at is kept: with no instant to count from, the rule cannot tell its age.

When the rule runs

  • A fresh read is sessions.state === "read" with readAt set. Bridge launches on a picture it kept on disk, which also arrives as read; readAt stays null until Fleet answers, so the disk picture never sweeps. A failed re-read keeps the last good list in the inputs, and the sweep ignores it as well.
  • The startup sweep and the running one are the same function over the same rule: it reads every kept job-panes:job: key and every owner held in memory, and drops the gone ones. One code path, so the startup case cannot drift from the running one.
  • The 10 minute spacing: the Job list arrives on every event, several a second in a busy turn, and a sweep lists every kept key. A Job crossing its 7 days does not need dropping to the second.
  • A Job whose panes are drawn in this window is never dropped, whatever the rule says. The store counts the owners drawn now; the sweep skips them, and picks them up on a later sweep once closed.

Dropping one owner of a family

Each family gets drop(id): it forgets the owner's kept key, removes its entry, ⌘Z history and measured area, and tells listeners. Opened again later, the owner is made fresh from the layout for all, as a Job seen for the first time is. The family's saved layouts and layout for all are untouched.

How Custom tab state is keyed and dropped

OptionWhat it costs
A. Mint tab ids unique across JobsFixes new tabs only. Kept arrangements already hold clashing ids, and the state still has no Job to drop it by.
B. One flat map keyed by jobId and tab id joinedDropping a Job scans every entry.
C. A map of Jobs, each a map of tabsDropping a Job is one delete. Every function in custom.ts takes the Job id first; all 9 callers already hold it.
  • The draft's key becomes custom:<jobId>:<tabId>, kept as session:custom:<jobId>:<tabId>.
  • forgetCustom(jobId) drops the Job's tabs from memory and every kept draft under its prefix. Part A's drop of a gone Job calls it, so the sweep clears both.
  • Old drafts under session:custom:<tab id> name no Job, so they cannot be moved to one. Pick: the first sweep forgets them. Cost: a Custom tab description typed and not sent before this lands is lost once. The other way, letting the first Job that opens the tab id adopt it, repeats the sharing bug once.
  • The seeded tab at id 900 in the job layouts mock stays as it is; it no longer needs to dodge a clash, and moving it is outside what was asked.

What this does not cover

  • Pull request panes on the Reviews page. Their pr-panes:pr: keys keep growing; this change only gives that family the drop it needs.
  • The Operator's panes. One owner, nothing to clean up.
  • The shared layouts of each family: saved layouts, the layout for all and their versions. They are one key per family and are left alone.
  • Any other per-Job state Bridge keeps under its own kept keys, such as composer drafts of a Job's thread, queued ideas or browser tabs. Only the two stores named in armada-vs8t and armada-20v4 are swept.
  • How tab ids are minted. They stay per window; the Custom tab state stops depending on them being unique.
  • Fleet. Nothing outside apps/desktop/src/renderer/src changes, and Fleet still keeps every Job forever.
  • A setting for the 7 days or the 10 minutes. Both are constants in the code.
  • How a layout or a Custom tab looks or behaves while its Job exists. Nothing changes there, apart from the one-time loss of old drafts named above.

What was not checked

  • How many job-panes:job: keys a long-used Bridge holds today. No real profile was read.
  • Whether any other surface reads a Custom tab draft by its old key. A search of apps/desktop/src/renderer/src found only custom-body.tsx.
  • Bridge was not started, so the sweep is proven by tests only.
