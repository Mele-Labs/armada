Background delivery: a Job ends at its push

Most of this exists already, and the build is smaller than the brief suggests. Fleet already runs gh pr merge --auto itself, reads every open pull request every 60 seconds, and can park a Job's slot and bring it back on the same branch with the same conversation, which is what pause and Resume do. What is missing is the trigger: a Job with Auto land on should be parked at its push, and woken by Fleet on red or conflict instead of by your Resume. Fleet should also merge main in itself when that is clean. One finding changes point 1: Jobs already run named tests rather than suites, and those still take 10 to 15 minutes, so the fix for that half is in how a Check spends its time.

The structural cause of the slow runs is compile contention. Each slot keeps its own warm target/, so a build is not cold for want of a folder. A named test in crates/fleet still links that crate's whole test binary, and every run on the Mac shares one compiler job pool sized four under the core count (crates/checks-runner/src/build_slots.rs). With eight running, each build gets a fraction of the Mac. The 900 seconds covers that build as well as the tests (crates/checks-runner/src/run.rs:290).

The flow

1. Before the push

Jobs already run named tests. In a week, 383 of 388 test runs named them. Telling Jobs to skip the suite changes little. Three changes do:

  • The compile gets its own budget. one_test gains a prerequisite that only builds (cargo nextest run --no-run). The runner already gives each prerequisite its own budget, so a squeezed build no longer eats the test's 900 seconds.
  • Rust type-check runs before the pull request opens. The runs_at: pre_pr mechanism already runs format_check for the TypeScript workspaces at that moment (crates/fleet/src/session_host/pre_pr.rs). The root typecheck joins it for the crates a change reaches.
  • The skills that say what to run before landing name only the tests the Job wrote, shown red then green. verify-before-done, implement-change and land-branch are reread for any line that sends a Job to a whole suite.

2. Hand-off at the push

When a Job's turn ends with its pull request open, Auto land on, a clean tree, everything pushed and nothing in Needs you, Fleet parks it. The slot goes back to the pool on the branch's tip, and the agent process ends. The Job reads Landing in the Work list until it merges. The same rule already gives a slot back once its pull request merges (docs/concepts/fleet.md, the Merged row), so this moves the moment earlier rather than adding an act. The agent needs to do nothing new: all_done stays refused while the pull request is open, as today.

A Job with Auto land off keeps its slot, because you may still ask it for changes before you merge.

One addition: a merge queue failure on a branch whose own pull request run was green is queued once more before the Job is woken. Fleet already reruns a hung job once without telling anyone (pull_notices.rs:354). On 4 Nov, 8 queue runs failed in a row, mostly desktop_unit. Fixing those tests is the separate Job, and this only stops a red the branch did not cause from waking an agent.

Beads gates or Fleet's own reading

Recommendation: Fleet's own reading of the pull request wakes the Job. A beads gate can mirror the wait into the backlog, and the mechanism does not depend on it.

Beads 1.3.2 has gates that block a step until a condition holds. Fleet would run bd gate check on its own timer, and bd ready --gated lists what just opened. Read from bd gate check --help:

Gates would not replace the reading, because they miss conflicts and queue drops and see red only run by run, so Fleet would keep its loop and add a second one. They also tie the wake to the tracker a repository chose. A repository whose tracker is not beads, and a Job with no issue, would have no gate, while the hand-off has to work for every Auto land Job. What a gate adds is a record in the backlog: the Deliver bead reads blocked until the pull request merges. If you widen your use of beads, that record costs one write when Fleet parks the Job, through the plan mirror (crates/fleet/src/plan_mirror.rs), and one when it merges. That can come later without changing the hand-off.

5. Your preview

scripts/preview merges only branches that sit in a slot, so a parked Job would drop out of it. The preview reads the Landing branches from Fleet as well, and leaves out any Fleet reports merged. It still restarts only when you press Refresh preview. That was your decision (crates/fleet/src/building.rs:15), and this does not change it.

6. A timeout reads as timed out

The runner already knows the difference: Exit::TimedOut (crates/checks-runner/src/run.rs:328). It is lost at crates/armada/src/session_checks.rs:147, which passes only "exit code 0 or not". The fix carries a timed_out state through the store, the wire (crates/ipc/src/session_checks.rs:13) and Bridge, with its own glyph and a tooltip naming the limit. The run's time is measured from when the Check took its slot rather than from when it started waiting, which is why runs show up to 1,134 seconds against a 900-second limit. The log ends with the line that says it was stopped at the limit.

What was not measured

  • How much of a run's time was waiting for a Check slot and how much was compiling. The store does not split them, and fixing that is part of section 6.
  • How many slots Jobs with an open pull request held at the peak. The brief's "every Job holds its slot" was not counted.
  • How many of the 226 failed named runs were deliberate reds, compile errors or real failures.
  • Whether --no-run as a prerequisite reuses the build for the test run in every case. Both use the same profile and target, so it should.
  • Whether a resumed conversation keeps enough context after a day in Landing. Long Jobs already resume after the 10-minute quiet timeout, which suggests it does.
